## 1. 目标与非目标

### 目标

治「**左尾时段性劣化**」：渠道整体中位速率不变，但一部分请求的生成速率塌到正常值的 1/10~1/20，且这种塌陷**成时段出现**（不是单发偶发）。

wb（provider_id=167）09-21 14:00 起的实测形态即此类：

| 指标 | 健康段 09:00–13:30 | 劣化段 14:00–14:58 |
| --- | --- | --- |
| n | 1684 | 278 |
| p05 | 184.1 | **10.5**（塌 17.5 倍） |
| p50 | 240.3 | 204.3（**几乎不动**） |
| `r<50` 占比 | 1.78% | **26.26%** |
| `r<150` 占比 | 3.56% | 39.93% |

判据要点：**中位数不动、左尾塌**——这正是「首字很快但输出极慢」的指纹（首字节由 TTFB 决定，未受影响；塌的是首字节之后的生成阶段）。

### 非目标

| 不做 | 理由 |
| --- | --- |
| 不替代熔断 | 熔断治「连不上/报错」，本机制治「连得上但生成慢」。两者判定输入正交（错误分类 vs 速率），且已有独立的 `health` 包状态机 |
| 不治「整体掉速」 | 若某渠道 p50 整体下降（如上游全面限流），那是渠道级容量问题，应由运维下线该渠道，而非逐请求降级 |
| 不做上游侧重试/整流 | 那是 `rectify` 包的职责面 |
| 不做跨渠道竞速策略变更 | hedge 已有自己的阈值与闸门，本机制只改「候选排序」，不碰竞速 |

### 用户已拍板的三条（不得改）

| 编号 | 裁决 |
| --- | --- |
| D1 | 基线粒度按「**渠道 × 模型**」：a 渠道 b 模型的历史速率作基线，低于其一定比例即算低速 |
| D2 | 采集开关**每个供应商渠道单独设置，默认全部关闭**（只对部分渠道开启） |
| D3 | 主要针对 **wb（provider_id=167）** |

## 2. 低速判据

### 结论

一条请求记为「低速样本」当且仅当**四条同时成立**：

| # | 条件 | 理由 |
| --- | --- |
| 1 | `status_code = 200` | 失败请求的 duration 不含正常生成语义 |
| 2 | `output_tokens >= 50` | 样本量下限：短输出速率受帧解析与网络往返主导，与生成能力无关。1-token 工具调用没有速率可言 |
| 3 | `first_byte_ms` 非空且 `duration_ms > first_byte_ms` | 分母必须为正；`first_byte_ms` 空则无法分离 TTFB 与生成阶段 |
| 4 | `generationRate < 低速线` | 见 §3 的阈值推导 |

### 速率公式

```
generationRate = output_tokens / ((duration_ms - first_byte_ms) / 1000)    单位 tok/s
```

**复用既有口径**，不新增第二套度量：`pubstatus/rollup.go:571` 的 `ComputeTokensPerSecond(outputTokens, durationMs, firstByteMs)` 定义逐字相同（`outputTokens <= 0` 或 `generationMs <= 0` 时返回 nil）。

### 首字节语义（决定样本清洗）

`first_byte_ms` 是「上游首个**非空 chunk** 相对请求开始的延迟」，不是提交时刻——`forward/observe.go:88-90` 与 `forward/stream.go:149-151` 已显式区分。

**必须剔除的伪高值**：`first_byte_ms / duration_ms > 0.9` 的样本。实证：`r >= 500` 的样本里 **92%~97%** 满足该条件，中位 `duration_ms - first_byte_ms` 仅 89~128 ms——**这是非流式（整包）一次性到达**，首字节≈末字节，分母被压到近乎 0，速率爆炸成假值。148 渠道 1370 条 `r>=600`（占其 17.8%）基本全属此类。

清洗不改变分布形态（167 峰值桶 220-240 由 1777 降到 1756），只砍掉假尾。

### 流式与非流式

**同口径，无需分叉**：`duration_ms` 与 `first_byte_ms` 两列对流式与非流式都有值；清洗条件（`fb/dur <= 0.9`）已把「整包响应」这类非流式的畸变形态挡在外面。

## 3. 基线口径与阈值推导

### 结论

**基线 = 该（渠道 × 模型）历史中位数，阈值 = 基线 × 系数（默认 0.2）。不用分位数做判定阈值。**

```
基线        = median(该渠道该模型最近 N 天的 generationRate，已过样本清洗)      N 默认 3 天
低速线      = 基线 × SLOW_RATE_RATIO                                            系数默认 0.2
判定        = generationRate < 低速线
```

wb 验算：历史中位 241.1 × 0.2 ≈ **48 tok/s**，与实测的劣化段慢请求中位 **17.2 tok/s** 分界吻合（劣化段 `r<50` 占 26.26%，健康段 1.78%，区分度 15 倍）。

### 为何不用 P20（会诊稿原方案）——实证否掉

opus 会诊稿主张 `低速线 = P20(该渠道该模型过去 10 分钟)`。生产实证给出三条否证：

**否证一：P20 与「慢」无对应关系。** wb 分布是**单峰 + 右长尾**（不是双峰）。P20=215.2 tok/s 落桶 **200-220**，左邻桶 366 条 / 本桶 1229 条 / 右邻桶 1777 条——**单调上升，在主峰上升沿之内**，既不是低峰也不是谷底。P20 切掉的只是主峰左肩的 20%。

**否证二：触发率被定义钉死在 20%，对变慢零敏感。** 八组渠道全部落在 19.9%~21.2%，无论分布宽窄（167 的 sd=51.5 与 148 的 sd=9502 触发率同为 20.00%）。意味着每 5 条正常请求误判 1 条，且永不收紧。

**否证三：两种基线取法在劣化段都不成立。**

| 基线取法 | 健康段触发 | 劣化段触发 | 问题 |
| --- | --- | --- | --- |
| 冻结的全局 P20 | 22.1% | **57.2%** | 严重误杀（超半数正常请求被判低速） |
| 时段内重算 P20 | — | **20.1%（恒定）** | 分位自我实现：阈值追着数据跑，永远抓不到 |

### 三口径对比（劣化段 n=278，实测）

| 口径 | 健康段 | 劣化段 | 评价 |
| --- | --- | --- | --- |
| 冻结 `r<P20` | 22.1% | 57.2% | 不可用 |
| `r<P50×0.5` | 3.0% | 37.1% | 可用但偏紧，对宽分布渠道退化 |
| `r<mean×0.5` | 3.0% | 37.1% | **必须与样本清洗绑定**（未清洗时 148=80.52%、145=78.30% 灾难性误杀） |
| **绝对阈 `r<50`** | **1.78%** | **26.26%** | **判别力最强** |

本稿取「历史中位数 × 系数」推绝对阈，理由：① 中位数不受右尾假值与左尾慢样本拖动（劣化段 26% 慢请求会拖低均值，中位数纹丝不动——实证已证，p50 204.3 vs 健康 240.3）；② 绝对阈在 wb 上判别力最强；③ 跨渠道可比（不同渠道基线不同，但系数语义一致）。

### 基线窗口与重算

| 项 | 取值 | 理由 |
| --- | --- | --- |
| 窗口长度 | 默认 3 天 | 实证覆盖 4 天；更长会把已下线的旧形态算进基线 |
| 重算频率 | 每小时一次（定时任务） | 基线是慢变量；按天实测 wb 的 p20 在 207.1~219.9（±3%）稳定，无需更密 |
| 样本下限 | 该窗口内 ≥ 100 条有效样本 | 低于此不发布基线，该组合视为「无基线」，不做低速判定（fail-open） |
| 冷启动 | 新上线渠道/模型在攒够 100 条前不判定 | 避免用几条样本定基线 |

### 基线缺失：**最近 3 天无请求怎么处理**（关键缺口）

「最近 3 天」这个窗口在真实生产里经常是空的。必须区分四种「空」——它们的成因、后果、处理**完全不同**，混为一谈会导致两种事故：把冷渠道永久判死，或让刚重启的渠道用陈旧基线误杀。

#### 四种情形与处理

| # | 情形 | 判定依据 | 处理 | 理由 |
| --- | --- | --- | --- | --- |
| **A1** | 渠道新建，从未有过请求 | 该组合在 `message_request` 里**全期**无行 | **不判定**（no-baseline，fail-open） | 无数据可依。此时渠道通常处于「刚接入待观察」，本就不该被降权 |
| **A2** | 渠道曾有请求，但最近 3 天静默（< 样本下限） | 全期有行、但 3 天窗内有效样本 < 100 | **回退到扩展窗取基线**，标注 `baseline_source=extended` | 静默 ≠ 慢。渠道可能只是没被选中（分组/时段/熔断导致），用陈旧基线仍比无基线好 |
| **A3** | 渠道长期静默（扩展窗也无足够样本） | 3 天窗与扩展窗**都** < 样本下限 | **不判定**（no-baseline，fail-open） | 长期无流量意味着「即使误判也没影响」——没请求可降权；且无数据支撑 |
| **A4** | 渠道刚从故障/下线恢复 | 3 天窗内有样本但 < 100，且扩展窗内样本充足 | 同 **A2**（扩展窗基线）**但降级使用**：`baseline_source=extended_stale`，只做**会话级**降级，不做渠道级 penalty | 陈旧基线可能已不反映恢复后的真实速率。渠道级 penalty 影响面大，宁可不做；会话级只影响单会话，风险可控 |

#### 扩展窗的具体定义

```
主窗   W1 = [now-3d, now]        样本下限 100
扩展窗 W2 = [now-30d, now-3d]    样本下限 100   ← 追加，非替换
```

**取 W2 的中位数**（不是 W1∪W2 合并）：

- 若 W1 已达标 → 用 W1，`baseline_source=primary`
- 若 W1 不达标且 W2 达标 → 用 W2，`baseline_source=extended`（A2）
- 若 W1 与 W2 都不达标 → 不发布基线（A3）；**但若 W1 有 ≥ 10 条样本**，仍发布 `baseline_source=extended_stale`（A4）

**为何取 W2 单独的中位数而非合并**：合并会让陈旧数据稀释当前形态。W2 单独算，至少口径一致（都是「某个 3 天窗口的中位数」），且能在日志里明确区分来源。

**为何 30 天**：与基线键 TTL（7 天）无关——W2 是**查询窗口**不是缓存窗口；30 天覆盖多数「静默但未下线」的场景，同时避免查到早已不存在的旧形态。若 `message_request` 保留期短于此，按实际保留期截断（见下）。

#### 数据保留期约束（必须实施前核）

`message_request` 有保留策略吗？若历史行会被清理（如只留 30 天），则：

- W2 的实际上限 = `min(30d, 表内最老行的 age)`
- 定时任务查询时用 `GREATEST(now-30d, MIN(created_at))` 之类的下界，避免全表扫
- **实施前必核**：查 `message_request` 的实际保留策略与行数分布（若无清理，则全期可用；若有清理，W2 上限随之收缩）

#### 「长期无流量」与「无基线」是两回事（勿混）

| 概念 | 含义 | 后果 |
| --- | --- | --- |
| **无基线**（no-baseline） | 无法判定该组合是否低速 | 不生成 penalty、不写状态键；选路时该渠道**按原有优先级参与** |
| **长期无流量** | 该组合最近没有请求 | 采样键/状态键 TTL 到期自然消失（§5）；但**基线可保留**（W2 回退） |

一个渠道可以「有基线但无近期流量」（选路不选它），也可以「无基线但有流量」（新渠道刚接入）。前者用 W2 兜底，后者 fail-open。

#### 与样本下限的关系（阈值分层）

三个下限必须分清，不可混用：

| 名称 | 取值 | 用途 | 不满足时 |
| --- | --- | --- | --- |
| **基线样本下限** | 100 条 | 决定**能否发布基线**（中位数是否可信） | 回退 W2（A2/A4）或不判定（A3） |
| **判定样本下限** | 100 条 | 与基线同值。样本不足时中位数的标准误过大 | 同上 |
| **滑窗触发次数** | 3 次 | 决定**是否标记**（§5 状态机） | 保持当前状态不变（fail-open） |

前两者取同值（100）不是巧合：**基线可信度与判定可信度依赖同一组数据的稳定性**，用两个不同数字会制造「基线看似可信但判定不该做」的灰色地带。

#### 边界情形补充（并入 §5 边界表）

| 情形 | 处理 |
| --- | --- |
| W1 与 W2 都无样本（A1/A3） | 不判定；**不写基线键**（避免读到空值）；选路侧该渠道无 penalty |
| W2 有样本但已过期（跨版本/跨模型形态变化） | `baseline_source=extended`；**首次使用时先打一条 info 日志**（供人工复核），后续静默 |
| 模型下线后重建（同名模型） | 视为新组合（A1）；基线从头攒。**不可**用旧基线——同名不同形态会造成系统性误判 |
| 渠道被停用期间（无请求） | 同 A2/A3；停用与慢无关，不应因此被降权 |
| 定时任务单次查询超时 | 保留上轮基线键（不删），打 warn；下轮重试。**禁止删键**——删键会导致该组合瞬间变 no-baseline，penalty 消失，可能引发抖动 |

### 基线漂移：**必须按组合独立评估**

实证的关键警告：**「最近几天的平均速率」这个口径只有部分渠道站得住**。

| 组合 | 按天 p20 摆幅 | 可用性 |
| --- | --- | --- |
| 167/wb deepseek-v4.1-flash | 207.1~219.9（**±3%**） | 可靠 |
| 148 deepseek-v4.1-flash | 186.5~237.2（±12%） | 尚可 |
| 156 deepseek-v4.1-flash | 134.4→245.2→239.0→162.0（**1.82×**） | 不可靠 |
| 74/claude-opus-5 | 312.5→55.2→166.1（**5.66×**） | 不可靠（且样本少） |

**处理**：基线每小时重算，天然跟随漂移；且按天 p20 的稳定性仅作参考，**不作准入条件**——是否开启某渠道的低速监控由用户按 D2 自行决定（对漂移大的组合，用户可不开）。

**反面教材**：wb 按天 p20 仅 207.1~219.9（±3%）看似极稳，却完全掩盖了当天 14:00 的断崖。**按天聚合会把小时级劣化洗掉**——这正是判定必须用「短窗数次数」（§5）而非「长窗算均值」的根本原因。

## 4. 存储选型与键形制

### 选型：Redis 滑动窗 + 内存基线

| 数据 | 存哪 | 结构 | 理由 |
| --- | --- | --- | --- |
| **低速样本事件**（短窗） | Redis | ZSET，score=发生时刻，member=请求 id | 滑窗天然需要按时刻清理；ZSET 的 `ZREMRANGEBYSCORE` 一行清完 |
| **标记状态与惩罚**（长窗） | Redis | Hash | 字段少、读多写少 |
| **历史基线**（数日） | Redis + 进程内缓存 | String/JSON | 每小时重算，读频率高、写频率低 |
| **渠道开关与参数** | DB（`system_settings` 或 provider settings 列） | — | 用户可配、需持久、需随配置同步广播 |

**为何不用 DB**：滑动窗是**逐请求写**（高扇出 + 短寿命 + 自动过期），落 PG 会产生大量短命行、拉高写放大与 vacuum 压力，而它又不具备账务语义（丢了不影响钱）。Redis 已有 `pubstatus`（桶聚合）、`health`（熔断状态）两个同构先例。

### 键形制（沿用仓内 `cch:` 命名与 hash tag）

```
慢样本滑动窗      cch:slow:{<scope>}:samples         ZSET   score=unixMS, member=<requestID>
标记状态与惩罚    cch:slow:{<scope>}:state           Hash   slowCount / penalty / enteredAt / lastSlowAt
历史基线          cch:slow:{<scope>}:baseline        String JSON  {median, samples, computedAt}
```

`<scope>` = `{providerID}:{modelKey}` 形式，**带花括号作 Redis Cluster hash tag**（与既有 `cch:pfx:{scope}` 一致——同组合的多个键落同一槽）。

`modelKey` 取 `original_model`（跨供应商别名归一，与 `pubstatus.ResolveSuccessRateModelKey`（`rollup.go:598`）同一口径），避免同一模型的不同别名各算一套基线。

### TTL 与自清理

| 键 | TTL | 说明 |
| --- | --- | --- |
| `:samples` | 窗口长度 × 2（默认 1200s） | 给窗口一个冗余，实际靠 ZREMRANGEBYSCORE 按时刻精确清理 |
| `:state` | 同上 | 与 samples 同寿命；样本全过期后状态自然消失 |
| `:baseline` | 7 天 | 基线是慢变量；过期后由定时任务重建 |

**长期无流量自动复位**：TTL 到期后键消失 ⇒ 冷启动、无历史惩罚（与 opus 稿的「窗口自清理」一致，本稿保留）。

### 写入点与异步一致性

写入走**异步终态队列**（生产 `MESSAGE_REQUEST_WRITE_MODE=async`）：

- 挂点：`terminal/settle.go` 的终态提交后动作（与既有 `affinityWriteback` 同一位置）。
- 与行写入**同队列、同顺序**：`terminal/batch.go` 的 `afterCommit` 已改为吃队列的写入 ctx（不吃请求 ctx），故请求返回后仍能完成写入。
- **一致性结论**：慢样本与 `message_request` 行同生同灭——进程崩溃时队列里未落库的那批行与它们的样本一起丢，**不会出现「行在而样本缺」或反之**。

### 逐请求开销

| 阶段 | 操作 | 实测预估 |
| --- | --- | --- |
| 写入（终态，异步） | 1 次 pipeline（ZADD + HSET + EXPIRE） | +1~3 ms，**不阻塞主路径** |
| 读取（选路） | 每候选 1 次 HGETALL（仅开启监控的渠道） | 见 §8 的零开销保证 |

内存：按 opus 稿估算，100 渠道 × 20 模型 × 10 分钟窗 ≈ 48 MB（可接受）；本稿因只对**已开启的少数渠道**统计（D2），实际远低于此。

## 5. 状态机与转移

### 结论：三态 + 两条阈值

```
        连续命中阈值次数              窗内再无低速样本
  正常 ======================> 已标记 ======================> 正常
   ^                            |
   |        （窗内无低速）         |  窗内再次低速
   |                            v  （不重置，累计）
   +-------------------------- 已标记（惩罚加深）
```

| 状态 | 进入条件 | 行为 | 退出条件 |
| --- | --- | --- | --- |
| **正常** | 初始态 / 已退出 | 无惩罚，不参与选路调整 | 窗内低速次数 ≥ 阈值（默认 3） |
| **已标记** | 上述 | 优先级 +penalty；若已开会话级降级则同时在该会话内排除 | 见下「恢复」 |

### 恢复：**采自然衰减，不采「整窗 0 次才移除」**

用户原方案要求「只有一整个窗口期内一次低速都没有，才移除标记」。本稿**建议改为自然衰减**，理由三条：

1. **「整窗 0 次」在时段性劣化下几乎不可达**：wb 劣化段 11 个连续 5 分钟段**无一例外**都有慢请求，而窗内只要再出现 1 条低速就重置倒计时，标记会长期不退出。
2. **ZSET 滑窗已经天然提供衰减**：旧样本按时刻被 `ZREMRANGEBYSCORE` 清掉，`slowCount` 随之下降，penalty 自动回落。这是现成机制，无需第二条退出路径。
3. **严格退出会造成振荡**：若渠道在「略低于阈值」与「略高于阈值」之间摆动，严格退出会变成「标记-退出-标记」的抖动，而衰减只是让惩罚平滑起伏。

**折中（保留用户的直觉）**：状态在「**窗内低速次数降为 0 且持续一个 TTL**」时才从 `已标记` 回到 `正常`；但**惩罚值**随样本过期**连续衰减**。即：

| 方面 | 行为 |
| --- | --- |
| 惩罚值（影响选路） | 连续衰减（样本过期就降） |
| 状态（供观测/告警） | 严格：窗内 0 次低速 且 保持一个窗才回正常 |

这样既不违背用户「要彻底干净才摘标记」的直觉，又不会让惩罚长期硬挂。

### 边界情形

| 情形 | 处理 |
| --- | --- |
| 窗内样本不足（低于 `样本下限`） | 不判定，保持当前状态不变（fail-open，宁可少标不可误标） |
| 长期无流量 | 键 TTL 到期自然消失（冷启动） |
| 同时被熔断 | **两者独立，不合并**：熔断在 `health` 包、低速在本机制；选路时熔断先过滤（硬排除），低速只调优先级（软降权）。被熔断的渠道本就不在候选集，低速惩罚对它无意义 |
| 渠道被停用/删模型 | 配置同步事件到达时清掉该 scope 的键（由定时任务顺带清扫） |
| 基线不存在（未攒够样本） | 不判定（fail-open） |

## 6. 惩罚公式

### 用户原式的问题

原式：`penalty = floor(次数 / 设置次数 × 惩罚基数)` ，基数默认 10。

| 次数（阈值=3） | 原式结果 | 问题 |
| --- | --- | --- |
| 3 | `floor(1.0 × 10) = 10` | 正常 |
| 6 | `floor(2.0 × 10) = 20` | 已经开始失控 |
| 30 | `floor(10 × 10) = 100` | **超出 priority 全量程**（生产常见量级 0~30）⇒ 该渠道**实际上永久不可达** |

两个毛病：① **无上限**，惩罚会把渠道挤出可选集，形成「渠道饿死」（没有流量 → 没有新样本 → 惩罚不降 → 永不恢复的正反馈）；② 线性放大太快，几次额外慢请求就跳到不可达区。

### 定稿式

```
slowLevel = floor(slowCount / thresholdCount)            每满一档进一级
penalty   = min(slowLevel × penaltyStep, penaltyMax)
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `thresholdCount` | 3 | 触发阈值（用户设置的出现次数） |
| `penaltyStep` | 10 | 每档增加的优先级量（用户的「设置增加优先级默认 10」） |
| `penaltyMax` | 30 | **上限**，防渠道饿死 |

对照（阈值 3、步长 10、上限 30）：

| slowCount | 3 | 6 | 9 | 12 | 20 | 50 |
| --- | --- | --- | --- | --- | --- | --- |
| 原式 | 10 | 20 | 30 | 40 | 66 | 166 |
| **定稿** | **10** | **20** | **30** | **30** | **30** | **30** |

上限取 30 的理由：生产 `providers.priority` 与 `group_priorities` 的常见取值在 0~30 量级，+30 足以把被标渠道推到最低档，但不至于无法被选中（其它渠道全熔断时仍能兵底）。**上限可配**，默认 30。

### 生效层：**必须落在优先级解析层，不能新建过滤层**

这是本节最关键的实现结论。

**错误做法**：在选路里加一个「低速过滤」把被标渠道从候选集里排除。后果：
- 与熔断的硬排除重叠，两套排除机制语义模糊；
- 被排除的渠道在 `decisionContext` 里会变成「不可见排除层」（仓内已有此类观测缺陷：候选既不在 `candidatesAtPriority` 也不在 `filteredProviders`，事后无法归因）；
- 丢掉了「软降权」的本质——低速不是硬故障，不该彻底不可选。

**正确做法**：把 penalty 加在**生效优先级**的**唯一漏斗内部**：

```
resolveEffectivePriority(provider, userGroup)  // route/rules.go:86-110，函数体 25 行
  └─ 返回值 = 分组覆盖 ?? provider.priority ?? 0
       ↑ penalty 加在这里，且**必须在覆盖判定之后**
```

**为什么必须在这个函数内部改**（实证，非推断）：该函数是**全仓分层的唯一漏斗**——非测试调用点 **22 处**，覆盖 `select.go`（亲和短路、`SelectedPriority`、consideredCandidate、`selectTopPriority`、`priorityLevels`）与 `simulate.go`（模拟预览），见 `select.go:252/293/391/403/405/411/422`、`simulate.go:272/379/390/510`。在内部改 = 一次性覆盖全部读数；在外层包裹（包一层新函数） = 22 处仍走旧漏斗，**读数与实际选路分叉**（如 `SelectedPriority` 记的档位与实际排序不一致，界面归因就错了）。

**必须加在分组覆盖之后**，因为分组覆盖是第一真源（有覆盖时 `providers.priority` 列根本不参与排序），直接改列值会被覆盖吃掉、等于不生效。

**签名问题（实施必核）**：`resolveEffectivePriority(provider Provider, userGroup string) int` **无 `req`/`now`/penalty 形参**。要让 penalty 参与，两条路：

| 路 | 形状 | 代价 |
| --- | --- | --- |
| **A. 扩签名** | 加 `penalty int` 形参 | **22 处调用点全要改**；但每处改动都是机械的（传 0 或传实算值） |
| **B. 加读取器** | `Selector` 持有一个 penalty 读取器（如 `s.penaltyReader`），函数改方法或把读取器作包级注入 | 调用点不改；但引入包级状态（与仓内现有 `Selector` 持有 `opts` 的风格一致，倾向此路） |

**建议 B**：`Selector` 已是选路状态载体（`opts`、亲和、熔断读侧都在它身上），把 penalty 读侧也挂上去，函数改成 `func (s *Selector) resolveEffectivePriority(provider Provider, userGroup string) int`。这样 22 处只需改接收者写法（或保留包级函数 + 包级读取器，零改动）。**具体选型在 B4 实施时定，不阻塞 B1~B3**。

**留痕要求**（避免重蹈复辙）：penalty 必须写进候选条目。但 **不是**直接往 `decisionContext` 加非空 JSON 键——实证：`chain_test.go:94-112` 对 `decisionContext` 做**排序后键集精确断言**（金样本 13 键，`go/testdata/golden/message_request_row.json`），加非空键 **必红**。三条出路：

| 出路 | 做法 | 评价 |
| --- | --- | --- |
| **1. `omitempty` 且对拍场景为空** | 字段 `SlowPenalty int \`json:"slowPenalty,omitempty"\``；penalty=0（常态）时不出现在 JSON | **推荐**。金样本对拍时未开启监控，penalty 恒 0，键集不变，`chain_test.go` 零改动 |
| 2. `json:"-"` 不序列化 | 完全不进 chain | 违背留痕目的（界面看不到），不可取 |
| 3. 改金样本 + 改断言 | 手改 `go/testdata/golden/message_request_row.json` 与 `chain_test.go` | **禁止**：`AGENTS.md` §8 明令不得手改金样本 |

先例：`reason.go:313` 的 `ModelSupportedProviders int \`json:"-"\``（其注释 `297-312` 明写「加键即破坏对拍」）——仓内早已知道这个痛，走的是「诊断计数不进 JSON」。本机制不同：**penalty 是排障必需，要进 JSON**，所以取出路 1（`omitempty`）。

## 7. 生效面与选路集成

### 介入位置

在 `route/select.go` 的 `resolve()` 内，两个位置各改一处：

| # | 位置 | 改动 |
| --- | --- | --- |
| 1 | `filtered := s.applyFilters(...)` 之后、`selectTopPriority(...)` 之前 | 为每个候选算 penalty，得到调整后的有效优先级 |
| 2 | `selectTopPriority(filtered.healthy, req.Group)` | 分层取值改为「含 penalty 的有效优先级」 |

**为何在这两个点**：熔断/分组/模型支持等硬过滤已跑完（`applyFilters`），候选集已是最终可选集；此时再算 penalty 才能保证「penalty 只影响同一有效集内的排序」，不会让渠道因降权而跳过本可服务的请求。

### 亲和/粘性的交互（重要）

会话粘性（另稿）会短路选路。两者相遇时有两条可能：

| 选择 | 后果 | 本稿建议 |
| --- | --- | --- |
| 粘性优先，高速渠道被粘住也不换 | 用户体验稳定，但慢渠道会一直磨那个会话 | 会话级降级（§8）补上这一块 |
| penalty 优先，粘性也按 penalty 重算 | 粘性被破坏，缓存命中率下降 | 不采纳（与粘性目标冲突） |

取前者 + 会话级降级：**渠道级 penalty 管「新会话往哪分流」，会话级冷却管「已粘的会话如何逃脱」**。两者职责不重叠。

### 与竞速（hedge）的交互

本机制只改**候选排序**，不改竞速阈值与闸门。后果：被降权渠道仍可能作为竞速者被拉起（如果主选慢到超阈值），这是对的——竞速是单请求级的兵底手段，不应被渠道级降权阻挡。

但要防一神情形：被降权渠道**反复当竞速者并赢下**。若它赢了，它会成为新的主选并写回粘性绑定。**不额外处理**，因为「赢下竞速」本身就是它当时更快的证据（实证里 wb 的慢是时段性的，其他时段它可能是快的）——让它凭实测赢回位置，比用历史惩罚永久压制更合理。

## 8. 按渠道开关

### 落地形态

按 D2，低速监控**逐渠道独立开关，默认全关**。

| 项 | 取值 | 说明 |
| --- | --- | --- |
| 开关位置 | **providers 表新增独立列**（非 jsonb） | 实证：`providers` 表**没有** settings jsonb 列（`drizzle/0000_legal_brother_voodoo.sql:46-68` 逐列无此列）；仓内 jsonb 列（`model_redirects`/`group_priorities`/`allowed_clients` 等 6 个）**全部用于「键集随用户变化的字典」**，而固定 5 参数属「列即配置」形态，先例是 `circuit_breaker_failure_threshold` 一族 nullable integer（`drizzle/0012_elite_iron_patriot.sql:1-3`）与布尔列（`0087_nappy_lady_mastermind.sql:1` 的 `disable_session_reuse`） |
| 默认值 | **false / NULL** | 未开启的渠道行为与现状**逐字一致**；数值列可空，NULL 表示取代码默认值 |
| 逐渠道参数 | 窗口长度、出现次数、比值系数、步长、上限 | 都有默认值（10m / 3 次 / 0.2 / 10 / 30），渠道内可覆写 |
| 迁移 | **1 条**：加 1 个 boolean + 5 个 nullable integer 列 | 列名与默认值见 §10 |
| 前端 | provider 编辑表单增加「低速降级」分组（开关 + 5 个参数），zh-CN 与 en 两套词表同步 | 提交用小写 snake_case（如 `slow_rate_monitor_enabled`），显示/GET 用 camelCase——照 `group_priorities` 惯例（`src/types/provider.ts:293` vs `:362`） |

**列命名建议**（实施时可调，但必须与既有风格一致）：

```
slow_rate_monitor_enabled        boolean  NOT NULL DEFAULT false
slow_rate_window_seconds         integer  NULL
slow_rate_min_samples            integer  NULL
slow_rate_ratio                  integer  NULL   -- 千分比？还是 numeric？见下
slow_rate_penalty_step           integer  NULL
slow_rate_penalty_max            integer  NULL
```

**注：系数列的类型选型（实施前必须定）**：`系数默认 0.2` 是小数，而既有 `*_preference integer` 列全是整数。三条路：

| 选型 | 优点 | 缺点 |
| --- | --- | --- |
| `numeric(3,2)` | 语义直白（0.20） | 仓内无 provider 级 numeric 先例 |
| `integer` 存千分比（200 = 0.2） | 与现有 integer 列同形 | 需在读取处除 1000，略隐晦 |
| `integer` 存百分比（20 = 20%） | 同上，且人读直观 | 同样需转换；精度只到 1% |

**建议取千分比（`slow_rate_ratio_per_mille integer`）**：与 `group_priorities` 等 integer 列同形，无需引入 numeric；命名里带 `per_mille` 后缀消除隐晦性。其余 4 个参数都是整数，直接 `integer`。

### 未开启渠道的零开销保证

**硬要求**：未开启该功能的渠道，逐请求额外开销**严格为零**。保证方式：

| 路径 | 保证 |
| --- | --- |
| 写入侧 | 终态时先查「本渠道是否开启」（开关随配置快照常驻内存，不查 Redis/DB）；未开启即直接 return，不做任何 Redis 写入 |
| 读取侧 | 选路时**不遍历候选去查状态**，而是把「已开启监控的 providerID 集合」当白名单（内存中的配置快照）；集合为空时整段跳过（最常见情形：全关） |
| 内存 | 开关快照随 `cfgsync` 失效重载；进程内只有一个小集合，无逐请求分配 |

这条是设计约束而非优化：若未开启也要读 Redis，等于给全站选路凭空加一次往返（生产 5 个候选 × 每秒数百请求）。

### 会话级强制降级：**推荐进 MVP**

用户原方案要求：冷却期内该会话再遇低速率，就在会话内把该渠道标为不可用、强制降级。opus 会诊稿建议不做。**本稿推荐做**，理由与落点如下。

#### 为何应做

1. **渠道级 penalty 管不了已粘的会话**：粘性短路会让会话一直磨那个慢渠道（§7 交互表）。渠道级降权只影响**新会话**的分流，对已粘会话无效。
2. **仓内已有现成原语，复用成本低**（这是推翻 opus 结论的关键事实）：
   - `session/keys.go:52` 的 `ProviderCooldownKey(sessionID, keyID, providerID)`——**会话×供应商冷却键已存在**，带 hash tag；
   - `session/binding.go:251` 的 `Clear(ctx, sessionID, keyID, expectedGeneration, expectedProviderID, cooldownProviderID, cooldownTTLSeconds, ttlSeconds)`——已支持「带期望供应商的 CAS 清理 + 写冷却键」，**写侧完整**；TTL 落 `lua/clear-session-binding.lua:79-80` 的 `SETEX`。
3. **它才是用户手感的来源**：「我不想让同一个会话反复撞同一个慢渠道」——这正是用户提需求的起因（反复竞速、反复撞 wb）。

**注：但读侧通路全仓不存在（实施前必须知道）**：

| 侧 | 现状 | 出处 |
| --- | --- | --- |
| 键构造器 | 存在 | `session/keys.go:52-57` |
| 写侧（写冷却键） | 存在，但**生产零调用点** | `session/binding.go:270`（`Clear` 内）；生产代码里 `\.Clear(ctx` 无命中，只有测试调用 |
| **读侧（选路时过滤）** | **不存在** | `go/internal/route/` 与 `go/internal/session/` 均不读该键；全仓 `:cooldown` 只出现在键构造器、Lua、测试与文档 |

**结论**：所谓「复用现成原语」只成立一半——**键格式与写侧可复用，读侧必须新建**。工作量需按此修正（见 §10 B2/B4 量级）。

#### 落点

```
低速样本写入（终态）
  └─ 若该渠道已开启监控 且 本条为低速样本
       └─ 写会话冷却：ProviderCooldownKey(sessionID, keyID, providerID)  TTL = 冷却期

选路（route/select.go）
  └─ 候选过滤阶段：若该候选命中「本会话的冷却键」→ 排除
       （仅当本次请求带 sessionID；无会话 id 时跳过，回落到渠道级 penalty）
```

关键语义：冷却键是**会话×供应商**级的，所以它只影响那个会话，**不污染其他会话**——这正是「不把好渠道饿死」的保证（对比渠道级 penalty 是全站生效）。

#### MVP 边界建议

| 包含 | 排除（二期） |
| --- | --- |
| 会话级冷却键写入 + 选路过滤 | 冷却期内的指数退避（多撞多次则冷却期递增） |
| 渠道级 penalty | 按 endpoint 细分基线 |
| 逐渠道开关 | 管理面 UI 展示慢率统计/penalty 值 |
| 基线定时重算 | Lua 脚本优化（Go 侧 pipeline 已够） |

两者一起进 MVP 的理由：只做渠道级 penalty，用户观察到的「同会话反复撞慢渠道」现象不会消失——而那是他提这个需求的原因。

## 9. 风险评估

### 风险 1：prompt cache 命中导致速率差异（**实证已证伪，但仍登记**）

opus 稿担心缓存命中造成双峰分布、导致基线误杀。**实证否掉**：

| 组合 | cache>0 的 P50 | cache=0 的 P50 | 比值 |
| --- | --- | --- | --- |
| 148 | 269.4 | 237.7 | 1.13× |
| 167/wb | 241.2 | 227.5 | **1.06×** |
| 145 | 224.5 | 208.6 | 1.08× |
| 159 | 46.6 | 42.0 | 1.11× |

全部 ≤ 1.13×（阀值 2×），**缓存命中与生成速率无实质相关**。反证：wb 劣化段慢请求的 cache 命中率 **100%**、中位读量 44160（快请求 98% / 33920）——**慢请求几乎全在「缓存命中且命中量大」的场景**。

结论：不需为缓存做特殊处理。但登记在于：这一结论基于当前生产数据，若未来上游缓存策略变化（如引入缓存后处理），需重新验。

### 风险 2：长/短输出速率分布不同

**残留风险**：同一模型内，50~100 tokens 与 1000+ tokens 的速率仍可能不同（后者摊薄了固定开销）。

缓解：`output_tokens >= 50` 下限已挡掉最畸形的短输出；基线用中位数（不是均值）所以少量短输出的拖拽有限。**不做按 token 量分桶**（会让窗内样本量不足，得不偿失），登记为已知限制。

### 风险 3：并发争抢导致的偶发低速

自建渠道（如 Ollama）多请求并发时 CPU 争抢，全部降速。

缓解：阈值 3 次已能过滤单发争抢；滑窗 10 分钟后自动清。**残留**：若并发持续高于阈值，渠道被标记 → 流量减少 → 并发下降 → 速率恢复 → 标记退出。这是**自适应负载均衡**，符合预期。

### 风险 4：标记后正反馈致好渠道饿死（**最高风险**）

场景：渠道 A 因偶发 GC/网络抖动被标记 → penalty → 流量下降 → 窗内样本少 → 基线/统计不稳 → 更易被误标 → 流量再降。

三重缓解：
1. **penalty 上限 30 档**（§6）：即使最坏也只能降到最低档，**仍可被选中**（其它渠道全熔断时能兵底），不会永久不可达。
2. **会话级冷却只作用单会话**（§8）：其他会话不受影响，提供恢复路径。
3. **键 TTL 自清理**：长期无流量则冷启动，无历史包袱。

**残留**：若该渠道确实持续低速，正反馈是**正确行为**（它就该被降级），无需缓解。

### 风险 5：wb 式时段性劣化——**本机制的真实靶心**

wb 09-21 14:00 起的实测形态：

| 特征 | 数值 | 对机制的意义 |
| --- | --- | --- |
| 边界清晰 | 14:00 起连续 11 个 5 分钟段无一例外 | 滑窗能抓到 |
| 幅度大 | p05 184.1 → 10.5（17.5 倍） | 绝对阈区分度 15 倍（1.78% → 26.26%） |
| **中位数不动** | 240.3 → 204.3 | **故不能用「整体变慢」类阈值**，必须用左尾计数 |
| 前兆早现 | 10:00 起 min 已跌破 6 tok/s | 阈值需要能容忍少量前兆而不误报（阈值 3 次已覆盖） |
| 快请求占多数 | 劣化段 73.7% 仍正常 | 不能用全局均值/分位（会被正常请求主导） |

**结论**：本稿的「短窗数低速次数 + 绝对阈」正是为这种形态设计的。实证的「按天聚合会把小时级劣化洗掉」是反证——若基线用按天均值，wb 当天 p20 稳定（±3%），整个断崖会被平滑掉。

### 风险 6：样本清洗不严导致伪高值污染

若不剔除 `first_byte_ms / duration_ms > 0.9` 的样本，基线会被抬高，导致阈值偏高、漏检。

缓解：本稿把清洗作为**硬前置**（§2），写入时就判，不合格的样本**不入窗也不算基线**。

### 风险 7：缓存/存储故障

Redis 不可用时：

| 操作 | 行为 |
| --- | --- |
| 读写慢样本 | 静默跳过（fail-open）——不影响请求主路径 |
| 读开关快照 | 开关来自内存快照，Redis 挂了仍可判（除非 `cfgsync` 也挂） |

与仓内既有 fail-open 约定一致（亲和、熔断读侧均如此）。

## 10. 实现切分

### 分块与量级

| 块 | 内容 | 文件 | 量级 | 依赖 |
| --- | --- | --- | --- | --- |
| **B1 开关与配置面** | provider settings 覆写字段（开关 + 5 参数）、默认全关、配置快照读取面 | 2~3 文件（settings 结构 / 读取面 / 迁移） | ~120 行 + 1 条迁移 | 无 |
| **B2 样本写入** | 终态后写慢样本（清洗 + 仅开启渠道 + 会话冷却键） | 2 文件（新建 recorder + `terminal/settle.go` 挂点） | ~180 行 | B1 |
| **B3 基线定时任务** | 每小时重算（渠道×模型）中位数、写基线键、清扫失效 scope | 2 文件（新建 job + 注册） | ~150 行 | B1，可先于 B2 用历史数据回填 |
| **B4 选路集成** | 读 penalty / 会话冷却过滤、调整有效优先级、`decisionContext` 加 `slowPenalty` 字段 | 2~3 文件（`route/select.go` + 新建 reader + chain 留痕） | ~200 行 | B3（无基线时不判定） |
| **B5 前端与词表** | provider 表单分组、zh-CN/en 词条、类型定义 | 4~5 文件 | ~150 行 | B1 |
| **B6 观测面**（可为二期） | 管理面列出各渠道慢率/penalty/是否标记 | 2~3 文件 | ~120 行 | B4 |

**总量级**：MVP（B1~B5）约 **800 行 + 1 条迁移**；含 B6 约 920 行。

### Lane 划分建议

```
Lane 1（主干、串行）：B1 → B2 → B3 → B4
Lane 2（可并行）：B5（前端与词表，依赖只有 B1 的字段名）
Lane 3（二期或收尾）：B6（观测面）
```

**为何 B4 必须最后**：它消费 B1（开关）、B3（基线）、B2（penalty 状态）三份产物；先写会造成接缝猜测（前两份设计稿在这上面都栽过）。

**B3 可用历史数据先回填**：基线是纯离线计算（SQL 聚合 `message_request`），不依赖样本键——可先跑一轮把基线写进去，这样 B4 上线时立即有基线可用。

## 11. 与 opus 会诊稿的差异

| 项 | opus 会诊稿 | 本稿 | 理由 |
| --- | --- | --- | --- |
| **基线口径** | `P20(该渠道该模型过去 10 分钟)` | **历史中位数（3 天）× 系数 0.2** | **实证否掉 P20**：落主峰上升沿、触发率恒 20%、劣化段误杀 57.2% |
| **基线窗口** | 10 分钟（短窗） | **3 天（长窗）+ 每小时重算** | 短窗会被劣化段本身污染（分位自我实现，恒 20%）；长窗抗污染 |
| **阈值形式** | 分位（自适应） | **绝对阈（基线×系数）** | 绝对阈在 wb 上区分度 15 倍（1.78% → 26.26%），分位只提供 20% 的固定区分度 |
| **惩罚上限** | `min(floor(count/threshold), 10)`（上限 10 档） | `min(floor(count/threshold)×step, 30)`（步长 10、上限 30） | 保留上限思想（防饿死），但保留用户的「每次增加 10」语义 |
| **恢复** | 窗口滑动自然衰减 | **惩罚衰减 + 状态严格退出（折中）** | 仅衰减会让观测面长期显示「已标记」；仅严格退出会振荡 |
| **会话级降级** | **MVP 不做**（理由：复杂度高、与渠道级冲突） | **推荐进 MVP** | 仓内已有 `ProviderCooldownKey`（`session/keys.go:52`）现成原语，“复杂度高”不成立；且它才是用户手感的来源 |
| **样本清洗** | 未提 | **硬前置**：剔 `fb/dur > 0.9` | 不剔则基线被伪高值抬高、漏检（148 的 17.8% 属此类） |
| **样本下限** | `outputTokens >= 50` | **同（采纳）** | 实证支持 |
| **分组粒度** | per-provider per-model | **同（采纳）** | 与 D1 一致 |
| **存储** | ZSET 滑窗 + Hash，键 `cch:slowrate:provider:{id}:model:{key}` | **同结构，键名按仓内惯例**（`cch:slow:{<scope>}:samples`） | 采纳 opus 的结构选型；键名改用仓内既有风格与 hash tag |
| **写入点** | `terminal.Settle()` 异步队列 | **同（采纳）** | 与行写入同队列保证一致性；afterCommit 已吃队列 ctx |
| **逐请求开销** | +1~3 ms | **未开启渠道严格为零** | D2 要求逐渠道开关，未开启的不该付这个钱 |
| **按 endpoint 分组** | MVP 不做 | **同（采纳）** | 键数膨胀，当前粒度够用 |
| **缓存双峰** | 主要风险，用 P20 缓解 | **实证证伪**（P50 比值 ≤1.13×） | 实测：慢请求的 cache 命中率 100%，缓存不是原因 |
| **按天聚合** | 未讨论 | **明确警告**：按天 p20 稳定（±3%）会掩盖小时级断崖 | 实证：wb 当天 p20 207.1~219.9，却掩盖了 14:00 的劣化 |

### 采纳 opus 稿的部分

| 项 | 说明 |
| --- | --- |
| Redis ZSET 滑窗 + TTL 自清理 | 结构选型成立（仓内 `pubstatus` / `health` 同构先例） |
| 异步写入不阻塞主路径 | 与行写入同队列 |
| `outputTokens >= 50` 样本下限 | 实证支持 |
| per-provider per-model 分组 | 与 D1 一致 |
| penalty 上限防饿死 | 核心洞见，本稿保留并加强 |
| 写入点挂 `terminal.Settle` | 正确 |
| 排除按 endpoint 分组 | 合理 |
